# Legacy Home Assistant cloud connector (0.2)

> **Retired for new links.** The [direct connection](HOME-ASSISTANT.md) replaces this connector. Integration 0.3.0b3 and later pair locally and cannot use console codes, so the console no longer issues them. Existing 0.2 links keep working until their owners migrate, and are managed on the console's **Older Home Assistant links** page (`#/home-assistant-legacy`): status, announcement permission and disconnection. The server's code exchange and connector routes remain for those links and for rollback.

Phoenix lets opted-in Jibos control Home Assistant Assist devices through an outbound authenticated TLS WebSocket. Owners installed the standalone [Phoenix integration](https://github.com/Paskooter/phoenix-home-assistant) 0.2, linked selected robots with a console code, and choose entity exposure using Home Assistant's own Assist controls. The integration does not require a public HA URL, port forwarding, an LLM, or a paid remote-access service.

The owner instructions, exact tested phrases, compatibility matrix, troubleshooting, upgrade/removal steps, and hardware limits are maintained in that repository's README and release notes. English commands use the built-in `home_assistant` conversation agent by default; owners can explicitly select Jev or another installed agent. Direct on/off phrases for lights, switches and common household devices, brightness, tested colors, and named scene/script phrases are selected before execution, as are requests the decision layer classifies as smart-home control ([routing](HOME-ASSISTANT.md#routing-and-voice-behavior)). `Ask Home Assistant to…` is the fallback for custom Assist sentences. Unclassified utterances never probe the executing conversation API. Recognized Hue lighting intents redirect for linked robots, and Hue setup/delete/help phrases are ignored for them; robots without a binding keep existing Hue routes. Answers inside an active skill remain with that skill unless a new wake phrase begins a global turn.

Integration 0.2.0b2 supports HA-assigned robot areas, strict local state questions, per-robot 30-second follow-up context, exact owner-selected Assist-exposed scene/script phrases, robot diagnostics, and opt-in native announcements. Queries execute no conversation agent or service. HA owns the area/entity mapping and rechecks exposure before follow-up or routine execution. A generic room command without an assigned robot area fails before execution. Relative brightness changes by 26 on HA's 0–255 scale, clamps at off/full brightness, and requires each target to be an on light with a usable reading. Native Jibo commands retain precedence over shortcut phrases, including classifier-resolved skill decisions. The optional [Jev 0.3.0b1 agent](https://github.com/Paskooter/ha-conversation-jev) adds local room, follow-up, color, brightness, and exact scene/script paths.

Each robot's **Announcement status** diagnostic sensor keeps local readiness and the minimum receiver version visible while its notify entity is unavailable. A local 30-second timer updates quiet-hours status without network requests and stops on unload. Protocol 1 links remain compatible with 0.2.0b1; its archive is unchanged, and an existing installation needs no immediate reinstall, although its older firmware label can still show 13.1.0.

Phoenix remains a trusted command origin. TLS, installation credentials and verified household bindings reject unrelated callers; they do not prevent an operator controlling the running server from originating home commands. The current release has no independent robot-to-HA command signature, direct LAN connection, or offline voice mode. See the integration's [trust documentation](https://github.com/Paskooter/phoenix-home-assistant/blob/main/docs/security.md).

## Server configuration

Use the authenticated Gateway configuration: `ETCO_hub_disableAuth=false`, `ETCO_hub_accountUrl` pointing to the private Account service, a provisioned Hub signing secret, and the same nonempty `ETCO_account_internalPeerToken` explicitly in Account, Gateway and Classic. Account needs its private Hub and Classic service URLs for verified robot status and native delivery. The native launcher and Compose definition pass these settings. An unauthenticated Gateway cannot enable home actions. Do not expose private Account/Hub/Classic listeners or `/internal/` routes to the Internet.

The browser links through same-origin `/api/home-assistant` endpoints. Add the dedicated `location = /api/home-assistant/connect` block from `deploy/nginx/phoenix.conf` to the portal's HTTPS virtual host. It must proxy to Account, forward WebSocket Upgrade/Connection headers, disable buffering, and allow the connector's 20-second ping interval. Preserve existing instance pages, branding, analytics, and other proxy locations. All owners use a trusted HTTPS Phoenix origin; HA's local address is never submitted to Phoenix.

Native releases must use `scripts/deploy-native-release.sh <reviewed-commit>`, with the launcher's `PHOENIX_DEPLOY_RUNTIME_DIR`. Require fresh Hub and OTA activity state and a full sixty seconds without new activity as described in [DEPLOYMENT.md](DEPLOYMENT.md). Account connector sockets and heartbeats are separate from Hub voice transactions and do not reset that quiet minute. Actual listen/execute/reply work uses the existing Gateway transaction and admission lifecycle. Do not bypass deployment guards.

## Authentication and storage

Only an authenticated owner can generate a code for their live owned robots. Codes have 80 bits of randomness, expire after ten minutes, work once, and persist only as SHA-256 verifiers. Generating a new code replaces that owner's pending code. A successful exchange returns a random installation credential once; Phoenix stores its verifier plus durable owner/loop/robot bindings. The HA config entry stores that credential locally. Status responses omit credentials and verifiers.

Commands originate from the Gateway's verified robot identity. Account rechecks its account ID, friendly ID, access-key ID, owner, and loop records. Client household IDs, context fields and tracing headers confer no authorization. Removing a robot, deleting an account, suspending a loop, or changing ownership invalidates access; transferring ownership back does not resurrect a revoked credential. Owner disconnect or integration removal revokes the installation. A loop suspension requires relinking after restoration.

Account persists `homeAssistantInstallations`, `homeAssistantCodes`, and `homeAssistantActions`. Existing store files load missing collections as empty. Codes and bindings use private atomic snapshots. Reverse-action admission and result tombstones require a durable file-and-directory fsync before dispatch; those records contain identifiers, bounded status, deadline and a payload digest, without announcement text. Back up the private account store before upgrading. Every rollback executable must preserve all three collections: the earlier connector release preserves codes and bindings but would discard action tombstones on its next ordinary write. Relinking cannot recover those tombstones. Deploy the collection-preserving compatibility release before this feature release so automatic health rollback also retains them; never restore an older Account snapshot to roll back code.

## Protocol and reliability

[Protocol version 1](https://github.com/Paskooter/phoenix-home-assistant/blob/main/docs/protocol.md) uses session and request UUIDs, bounded messages, a 7.5-second command deadline, and plain speech results. There is one pending command per robot and at most four per installation. The server sends only on a currently ready connector; it never queues or retries actions after disconnect. Late and duplicate results are ignored. HA persists request-ID tombstones before execution, discards expired work, and never replays commands after reconnect or restart.

A lost result can mean the action already executed. Jibo says he could not confirm it; he does not claim definite failure or run it twice. Partial success is spoken as partial. The integration corrects HA success responses that include currently unavailable targets rather than repeating an inaccurate success statement. Ordinary responses use the existing Jibo skill builder; HA text is escaped for ESML, never interpreted as markup.

## Native announcements

Announcements use a separate authenticated outbound robot WebSocket at Hub's `/v1/robot-actions`, requiring the tested receiver in BE 13.1.2 or later. BE 13.1.0 failed speech-adapter initialization; BE 13.1.1 corrected that adapter but failed receiver startup because of a browser timer binding. The corrected receiver passed native announcement completion, an idle-channel reconnect without replay, supplied-ASR preemption after confirmed native stop, and automatic normal-mode boot on one physical Jibo. [The accepted physical scope](parity/evidence/2026-10-04/home-assistant-next/README.md) also includes a confirmed light on/off cycle through the owner's existing connector. General OTA publication is a separate guarded step. Enabling the console permission alone does not add the receiver to older firmware. Existing Hub WebSocket proxying can carry that path. Block public `/internal/` URLs in both Hub and Classic virtual hosts; those routes still require the private peer token. The new connector capabilities are negotiated, so older HA clients receive no unsupported frames. Robot connection status uses live verified sockets, not persistent Classic reconnect markers.

The installation's owner must separately enable announcements in the console. Default permission is off. Account rechecks that permission, live household ownership, the exact active connector, payload digest and deadline after Gateway identity verification, immediately before native admission. Revocation or transfer during that verification prevents dispatch.

Keep `PHOENIX_RUNTIME_DIR` on durable private storage. Gateway's UUID/binding execution ledger under `robot-actions/outstanding.json` restores outstanding activity before its first startup heartbeat, including for an offline robot. Confirmed native stop/completion is required to clear it; storage failures retain quarantine. The native launcher uses its persistent runtime root, and Compose supplies a private named volume shared with OTA. This state is separate from both the Account deduplication ledger and transient deployment counters.

HA applies local quiet hours. Announcements use Jibo's current volume; supplied volume overrides are rejected because the tested native speech engine does not support per-utterance gain. Native completion must be acknowledged before success. Busy/offline/draining/expired requests are rejected, not queued. Cancellation and deadline expiry request a native stop; a swallowed stop error or lost acknowledgement cannot release execution activity. Uncertain requests are not retried. The native receiver keeps a private UUID-only marker across its restart, stops retained speech, and never replays it.

```sh
node --test packages/account/test/homeAssistant.test.js packages/account/test/homeAssistantNext.test.js packages/account/test/homeAssistantRobotAdapter.test.js packages/classic/test/homeAssistantPresence.test.js packages/gateway/test/homeAssistant.test.js packages/gateway/test/homeAssistant.next.test.js packages/gateway/test/robotActions.test.js packages/common/test/deploymentActivity.test.js

# From the separate integration checkout, with its documented test environment:
PHOENIX_SERVER_DIR=/absolute/path/to/phoenix .venv/bin/python -m pytest -q -s
```

The combined tests run disposable real HA 2026.8.1 and 2026.9.4 instances with synthetic devices, the actual built-in conversation agent, real Account persistence/authentication and Gateway robot envelopes, and an isolated TLS edge. They cover config flow, reauthentication/reconfiguration, reload/unload/removal, exposure, availability/partial success, deduplication, deadlines, reconnect, revocation, forged identity/context, ordinary routing conflicts, native announcement completion/cancellation, and real guarded quiet-minute observations. Native peers and provider HTTP in these tests are synthetic. Private physical evidence remains outside Git. A synthetic transcript-to-result latency excludes microphone ASR, Internet transport and robot TTS; it must not be represented as measured owner latency.

Forward home control retains the existing native cloud-skill response path. Announcements require a separate reviewed BE OTA; its source and artifacts stay in the private local `jibo-be` project, outside Phoenix and GitHub. Complete official-archive integrity and physical boot, UI, voice and spoken-delivery checks are required before a stable OTA offer. Do not infer hardware acceptance from synthetic WebSocket tests or SSM's `running` flag.

The focused Phoenix Home Assistant checks passed **69/69**, and the strict parity gate passed **43/43**. [Full integration CI](https://github.com/Paskooter/phoenix-home-assistant/actions/runs/37190564109) passed **66 cases on each HA version**, plus HACS and hassfest. Broader Phoenix tests retain pre-existing failures and are not reported as passing. [The sanitized release evidence](parity/evidence/2026-10-04/home-assistant-next/README.md) records archive integrity, the accepted physical scope, and remaining checks. Supplied-ASR native turns establish routing, device state and spoken completion; they do not establish fresh microphone recognition.
