## What was verified against the pinned source (not inferred)

I read the pinned Pegasus interfaces and hub consumer code directly in this
worktree's reference tree
(`reference/5c0a7390539663ba749d360de348a428c088505c/packages/{interfaces,hub,baseskill}/src`)
and confirmed each matrix row the schemas encode:

- **ListenResult precedence** (`interfaces/src/hub/response.ts:89-100`): match if
  `nlu.intent` non-empty OR non-empty entities (entities getter null-safe,
  `entities:null` = empty); else `noInput` if no ASR text; else `noMatch`.
  `envelope.js listenResultState()` is a line-for-line match. Test covers 13
  precedence cases incl. `entities:null`, missing ASR, empty text.
- **LISTEN mode**: `ListenMessageMode` = `CLIENT_ASR`/`CLIENT_NLU` only;
  hub throws `Invalid value for mode` on anything else
  (`hub/src/listen/ListenTransactionHandler.ts:245`). Schema enforces the enum.
- **TRIGGER**: `triggerData` is dereferenced eagerly at runtime
  (`hub/src/proactive/ProactiveTransactionHandler.ts:94`) so it must be present;
  `triggerSource` is only compared to `SURPRISE` (line 248), never enum-checked —
  schema accepts unknown sources (reproduces runtime, not the interface).
- **SKILL_REDIRECT hub→robot**: `hub/src/utils/TransactionHandler.ts:111-131`
  always wraps `match: {skillID, launch:true, onRobot}` plus optional
  nlu/asr/memo; `final` = isOnRobotSkill. Schema requires `data.match`, optional
  rest — matches.
- **PROACTIVE responses**: `emitMatchResponse` writes
  `data.match{skillID,onRobot,isProactive:true,launch:true,skipSurprises}`
  (final = onRobot); `emitNoActionResponse` writes `data:{}` `final:true`
  (ProactiveTransactionHandler.ts:246-275). Schema accepts both shapes — this is
  the "without rejecting valid optional fields" case.
- **Skill session trace nullability**: `baseskill/src/graph/GraphManager.ts:84`
  pushes `{nodeID, transition:null}` on every `enterNode` and returns the
  action/redirect before the transition is resolved (lines 85-91). A launch
  response therefore legitimately carries `trace:[{nodeID,transition:null}]`.
  **The salvaged schema typed transition as non-null `string`, which is stricter
  than the reference; this was the defect that made
  `packages/skills/test/graph.test.js` fail 30/30 in repro.** Fixed to
  `['string','null']`. (This is the sole strictness defect found.)
- **Manifest rules**: `hub/src/config/validation/SkillConfigValidator.ts` —

  (105-118); SettingsRule requires skill/key/matchRule strings + `EXACT|NOT`
  (209-226);  IHRule requires query/matchRule/value, `IHMatchMethod` enum, and
  **value ∈ number|boolean|array|null — strings and non-null objects rejected**
  (120-163); IHQuery requires type (`LastEvent|Count`) and validates
  query/personID/time offsets (166-190). All mirrored in the manifest schemas.
  Falsification-checked (below).
- **Analytics**: `interfaces/src/skill/analytics.ts` —
  `[skillName]: AnalyticsEntry[]`, each `{event, properties}`; events constant
  `Skill Entry`/`Skill Offer` (MIM opt-in). Schema permissive, open

- **Envelope base**: `interfaces/src/service.ts:9-37` BaseMessage

## What was inferred

- The `action:null` terminal **SKILL_ACTION** shape (GraphSkill on a terminal
  node emits `action:null, final:true, fireAndForget:true`). The `interfaces`
  `ActionData.action` is typed non-null, but `baseskill` graph skills return
  `ExitResponse` with no action on terminal nodes and Phoenix mirrors that
  (graphManager.js:33-47, `noop-skill` test). Inferred from Phoenix consumer
  behavior; the reference skill runtime's exact terminal emission wasn't
  re-derived this session.
- `additionalProperties` is deliberately left *open* everywhere except where the
  reference's own runtime validator is strict (manifest rule objects). The
  reference SkillConfigValidator does run `checkUnexpectedProperties` (rejects
  unexpected keys) on ContextRule/IHRule/IHQuery/settingsRule; the schema models
  the *typed* restrictions (required + enum) but not
  `additionalProperties:false`, so it is more lenient than the reference on
  unknown keys. This is a deliberate "don't reject valid" stance, but it is a
  real leniency divergence from the reference validator — flagged for root.
- A `LISTEN_LAUNCH` with only `memo` (no nlu/asr) is accepted as valid; the
  reference types require nlu+asr on LISTEN_LAUNCH but the redirect drive path
  can produce memo-only — schema stays permissive. Inferred, not exercised
  against the reference emitter this session.

### Falsification checks (stated explicitly)

1. **IHRule `value` typing** (`['number','boolean','null','array']`, rejecting
   strings) is the highest-risk assertion: the `interfaces` type allows
   `string`, but the hub's runtime validator rejects it. Checked the pinned
   runtime source (`SkillConfigValidator.ts:153-163`) and confirmed strings and
   non-null objects are rejected; then broke it (added `'string'` to the schema
   array), saw the new wire test fail with exactly the expected "IHRule value
   string rejected" error, and restored it. New test covers all four accepted
   types + string + non-null object.

   `transition:'string'`, the new test failed, restored to `['string','null']`.
   (This assertion was also verified by the real failing graph-skill test before
   the fix.)

## Divergences flagged for root (not fixed here — outside owned files/gateway

- **`constants.js:HubErrorCode` does not match the pinned `interfaces/src/hub/HubErrorCode.ts`.**
  Reference has exactly:
  `SKILL_NOT_FOUND`, `TIMEOUT_SKILL`, `TIMEOUT_PARSER`, `TIMEOUT_ASR`,
  `TIMEOUT_CONTEXT`, `TIMEOUT_TRANSACTION`, `ASR`, `PARSER`, `GENERAL`.
  Phoenix's enum adds `TOO_MANY_REDIRECTS`, `NOT_IMPLEMENTED`, `NOT_FOUND`,
  `INTERNAL`, `AUTH` and omits `SKILL_NOT_FOUND`, `TIMEOUT_TRANSACTION`,
  `PARSER`, `GENERAL`. Since `packages/gateway/*` already consumes the Phoenix
  values (e.g. `HubErrorCode.INTERNAL` as a fallback), changing the enum would
  require a coordinated gateway change — outside this task. The default
  `errorResponse()` uses `HubErrorCode.INTERNAL`, which is not a reference code.
  Wire impact: ERROR responses carry these codes to the robot, so root should
  decide whether to align.
- **`constants.ResponseType` omits `ASR` and `COMMAND`** (present in
  `hub/MessageType.ts`). The hub can emit these on the ASR/COMMAND wheel paths;
  Phoenix doesn't build them yet.
- **Leniency on unknown manifest-rule keys**: schema doesn't set
  `additionalProperties:false` on ContextRule/IHRule/IHQuery/queryRules though
  the reference rejects unknown keys there (`checkUnexpectedProperties`).
- **`IHRule.matchRule` vs `IHMatchMethod`**: schema enum is
  `['EXACT','NOT','GREATER_THAN','LESS_THAN']`, which matches the reference
  `IHMatchMethod` — OK.
