# A-05 OOBE recovery and SetupRobot candidate

Status: **unverified; pending root review**.

This candidate is based on `66dd5758b68bc58dfd3412eb30a2c03a37c8d20e` in
`codex/candidate-a05-oobe-20260908`. It adds the OOBE `ReconnectRobot`
operation and brings the loop-bound `SetupRobot` path in line with the pinned
controller for owner checks, suspended robot replacement, and deleted-loop
lookup. It also applies the source required `token`/`id` validation before a
SetupRobot token can be consumed.

For a bound token, the request account must own the active loop. A suspended
loop follows the source sequence: find or create the replacement robot,
detach the old and replacement robot associations through the existing loop
mutation helper, reread the loop, attach the replacement with an accepted
member entry, unsuspend, persist, and then return its credentials. A deleted
loop is excluded before ownership or replacement mutation. Reconnect validates
the required token and optional string id, consumes a valid token, and returns
`{ result: "Command accepted" }`; missing or expired tokens remain
unconsumed.

explicit transport qualification rather than a claim that SNS event counts
are identical.

## Open scope and dependencies

The shared Phoenix `findOrCreateRobotAccount` helper currently creates new
robots correctly but does not yet reactivate and save an existing inactive
robot. Root owns that source-backed repair in
`.parity/worktrees/a04-robot-reactivation-20260908`; the suspended replacement
path depends on it for an existing replacement account. The no-loop
`LoopController.create` path and its existing-robot semantics are unchanged.
The candidate does not add an obsolete-ID adoption route or perform public
SigV4 authentication for OOBE; the owner check is the source token-account to
loop-owner check. Full Mongo/Mongoose casting, SNS delivery, native OOBE
execution, and real household migration remain outside this candidate.
