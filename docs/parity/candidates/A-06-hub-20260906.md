# A-06 Hub client candidate (unverified)

This candidate is based on published runtime `051cce7a565062938b4d38b8069d993cffa35f46` and is limited to the network Hub provider plus its Account `getFriendlyId` prerequisite. It does not change Lasso, Person, Settings transport, the public front door, or source/reference artifacts.

The pinned source is `jiborobot/srv-settings-ws` at `0d37e1fd2f4fca40538fb470194a3c5daf2c9830`. `src/clients/account.ts:23-28` performs `GET /loopPopulated?loopId=...` and returns `loop.robotFriendlyId` without validating the value. `src/clients/hub.ts:29-38` awaits that prerequisite, interpolates the ID into `new URL('/v1/skills/settings/' + id, base)`, sends only `X-JIBO-transID`, and returns `response.skills`. The pinned `@jibo/server` 4.0.12 `dst/wreck.js:35-85` requests JSON, ignores HTTP status, rejects only a truthy decoded `error` payload, and converts parse failures through `Boom.badImplementation`.

The implementation adds a private source-compatible JSON adapter for this Account-to-Hub path. It preserves ordinary non-2xx JSON, truthy error envelopes and their Boom `output`/`data` fields, direct property-access boundaries for null responses, URL interpolation/encoding, missing transaction-header behavior, and JSON parsing on every response. Existing Person and Lasso adapters continue to use their previously reviewed transport helper.

The independent source/candidate control is `.parity/reviews/a06-hub-20260906`. The source TypeScript was compiled with the pinned runtime toolchain, then ran in the pinned Node `v8.9.4` image resolved programmatically from `docs/parity/evidence/2026-09-05/compatibility-pins.json`; the candidate ran on Node `v22.22.0`. The retained suite has 22 ordered unique cases covering normal and special friendly IDs, query encoding, missing/null/empty Account results, ordinary non-2xx JSON, Account and Hub error envelopes, malformed JSON, null/array/primitive Hub payloads, string status codes, false error flags, and an omitted transaction ID.

Results from `comparison.json`:

- 22/22 cases have exact method, path/query, body, source custom headers, and independently checked listener Host authorities. Node 22's fetch adds its own standard transport headers; those runtime-generated headers are recorded but excluded from the source custom-header comparison.
- 20/22 result/error records match completely. The two remaining records are malformed JSON where Node 8 reports `Unexpected token o in JSON at position 1` and Node 22 reports its engine diagnostic; `name`, `isBoom`, and the complete Boom 500 output fields match.
- No other result/error difference was observed.
- Two additional malformed error-envelope cases without `statusCode` are retained in `excluded-source-failure-cases.json`. The original BaseClient process throws Boom's constructor error from inside the Wreck callback and produces no result file; they are documented as an unhandled source failure and are not counted as passing controls.
