## Source basis

The frozen source's `BaseService.checkAuthentication` requires an exact
`Authorization: Bearer <token>` header, checks the hub secret before calling
`jsonwebtoken.verify`, and returns `name + ': ' + message` for verification
exceptions. Its `verifyClient` checks authentication before exact WebSocket URL
registration, so an invalid token on an unknown URL returns 401; a valid token
on that URL returns 404 with
`WebSocket url '<url>' has no handler`.

The source dependency is `jsonwebtoken@8.1.1`. With the configured string hub
secret, its default algorithms are HS256, HS384, and HS512. It reports
`jwt must be provided`, `jwt must be a string`, `jwt malformed`, `invalid token`,
`jwt signature is required`, `invalid algorithm`, and `invalid signature` as
`JsonWebTokenError` instances. `nbf` is checked before `exp`; both require
numeric claims, use exact `>`/`>=` boundaries, and have no implicit 30-second
grace. `TokenExpiredError` and `NotBeforeError` retain their source names.

The source client signs credentials with the default HS256 algorithm and sends
`Authorization: Bearer <token>`. Phoenix `sign()` remains unchanged, including
its HS256 header and `iat` behavior used by the A-02 portal contract.

## Candidate behavior

`packages/common/src/jwt.js` now verifies HS256/HS384/HS512 with source
canonical signature-text comparison, source-shaped malformed/signature errors,
source error classes, primitive/object payload decoding, numeric `nbf` and
`exp` validation, and deterministic clock/tolerance options for tests. JWT
payload JSON is parsed before algorithm/signature checks, headers use the
source binary decoding boundary, and the Node 8 null-claim wording is retained.
When the host V8 parser omits a position or reports a repeated character's
first occurrence, a bounded grammar scanner locates the first invalid UTF-16
code unit while leaving `JSON.parse` authoritative for validity. It handles
top-level JWT primitives as well as nested objects/arrays, valid strings,
malformed literals, numbers, and escapes. The source differential includes
regressions for repeated `t`/`x`/`a`/`e` characters and the modern NaN/Infinity
diagnostic forms.
The source's unsigned
`none` form is retained only when no key is supplied; the gateway rejects a
missing hub secret before reaching that path. The `sign()` implementation and
its HS256 output are untouched, and no npm runtime dependency was added.

`packages/gateway/src/index.js` prefixes verifier exceptions with their source
class name. WebSocket path matching now uses the exact request URL, including a
query string, and unknown paths return the source 404 message. Authentication
continues to run before path lookup; `disableAuth` skips only authentication.

The active gateway uses `ws@8.21.0`, while the pinned source uses `ws@3.3.3`.
The rejected HTTP upgrade response has matching status, reason text, body, and
byte `Content-Length`; the active library spells the case-insensitive header as
`Content-Type` where the source spells it `Content-type`. No application-level
header difference was introduced by this candidate.

The original review fixture at
[`h10-auth-differential.json`](../../../packages/gateway/test/fixtures/h10-auth-differential.json)
drives the original compiled `BaseService` and `jsonwebtoken` inside the
pinned `node:8.9.4-slim` image, then drives the candidate on the host runtime.
The retained initial artifact covers 34 token cases, 10 direct header/secret
cases, and 8 actual raw HTTP upgrade requests. The expanded root review input
adds 74 JSON payload cases and 6 direct raw-token cases, for 108 token cases,
6 direct cases, 10 authentication cases, and 8 upgrade cases (132 total).
The source and candidate probes normalize only runtime metadata and
case-insensitive HTTP header names.

The first comparison exposed four differences and the bounded repair addressed
all four: JWT payload JSON must parse before algorithm/signature checks; signed
JSON `null` must use Node 8's `Cannot read property 'nbf' of null` wording;
JWS header bytes use binary/latin1 decoding; and HMAC verification compares the
canonical signature text rather than accepting alternate base64url encodings
with equal decoded bytes. The expanded comparison then exposed and repaired
the host JSON diagnostic position/wording differences. Its normalized result
has zero differences across all 132 cases. Complete source and candidate
outputs are retained in
[`H-10-source-differential-20260906-expanded.json`](H-10-source-differential-20260906-expanded.json);

## Remaining scope and limits

This candidate does not implement asymmetric RSA/EC verification because the
hub contract supplies a shared string secret and the pinned library's default
algorithm set for that key is HS256/384/512. It does not change
`verifyAgainstAccount`, token claim authorization, HTTP account/classic
transactions, or token issuance. Explicit `jsonwebtoken` options outside the
shared-secret gateway call are outside this bounded surface.

The tests exercise the active `ws@8.21.0` network framing and compare it with
the pinned `ws@3.3.3` source behavior; they do not prove Node 8 runtime or
native robot acceptance. Root must review and run integrated/native controls
before deployment or H-10 acceptance.
