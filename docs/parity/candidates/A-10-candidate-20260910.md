## Candidate divergence (report to root, not in DIVERGENCES.md)

1. **Socket rejection code: source `404 TOKEN_NOT_FOUND` vs Phoenix `401 Unauthorized`.**
   `srv-notification-ws errors.ts` defines `TOKEN_NOT_FOUND` with `statusCode: 404`;
   `srv-entrypoint-socket-ws socket-server.ts` closes a bad connection setup with
   `err.statusCode` (→404). Phoenix writes `HTTP/1.1 401 Unauthorized` when the
   upgrade token is unknown/rotated-away. Both are a hard upgrade rejection that
   the consumer (`NotificationEmiter`) retries identically after `reconnectInterval`,
   so no client-visible behavior change is expected, but the **wire code differs
   (401 vs 404)**. Pinned by a test (`notificationLifecycle.test.js` #3). **Severity:
   low / cosmetic on the wire; flag for root.**

2. **Duplicate-connection handling: Phoenix deterministic, source racy.** Phoenix
   `attachSocket` closes the previous socket for the same tokenId before replacing
   it, and the old socket's `close` is guarded (`return` if it is no longer current).
   The source blindly writes `connectionCache[tokenId] = ws` and lets a *previous*
   socket's `close` handler call `close(tokenId)`, which then closes the **new**
   socket (source bug). Phoenix's behaviour is the sane interpretation of "one
   active socket per token" and avoids killing the replacement. Not a parity break;
   recorded for root.

3. **`deliver` on a non-open socket.** Source `deliver` calls `close(tokenId)` when
   the cached socket is not `OPEN`; Phoenix `deliver` returns `false` and leaves the
   row pending, cleaning up only when the ws `close` event fires (which the `ws`
   library does on peer drop). Row-retention semantics are identical (row stays
   pending → retried on poll/reconnect). Difference is inside a dead-socket window
   only. Recorded.

## Verified / inferred / unknown

### Verified (read and/or executed)
- Token document shape & rotation, response `{token}`, 64-byte hex token, 100-row
  global cap, `created`-asc ordering, 300 s TTL expiry, 15 s poll default.
- Socket auth by last-segment token only; unknown/rotated token rejected at upgrade.
- `GetStatus` 24 h connected window with no ownership check (matches source TODO).
- Frame = stringified full Notification doc; ack deletes only on successful send
  callback; error/throw/close keep the row pending; same-token reconnect replays
  only un-acked rows exactly once (falsified, then restored).
- Persistence across store reopen and full Classic restart (existing durability
  tests plus this candidate's reconnect test).
- Multi-account isolation across concurrent sockets and reconnects; `/{token}`
  root-segment upgrade works.
- Full `npm test` = 1012 / 1005 pass / 0 fail / 7 skipped; parity gate match 43/0.

### Inferred
- `markConnected`/`markDisconnected` short-circuit (Phoenix writes the store
  directly) is behaviour-equivalent to the source's `SocketConnected`/`SocketDisconnected`
  event→handler path; the durable `lastConnected` effect is the same.
- The `ws` server auto-pongs client pings, so the native client's 3 s ping / 120 s
  idle keepalive (native source) is satisfied; not exercised with a native peer here.
- The source's racy duplicate-connection behaviour would rarely be observed on a
  healthy network; Phoenix's deterministic close-of-previous is the intended state.
