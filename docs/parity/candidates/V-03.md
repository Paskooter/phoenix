# V-03 candidate: incremental production capture writer

Status: working candidate; lead review and parity verification are pending.

The production driver previously materialized the complete report with
`JSON.stringify(report)` and then made another complete `Buffer` (and, for
gzip captures, a third compressed buffer). The full 20,533-case capture could
therefore fail with `RangeError: Invalid string length` after case execution
had completed.

This candidate adds `scripts/parity-production/capture-writer.cjs`. It walks
the report one object property and array item at a time, emits strings in
16 KiB chunks, honors writable-stream backpressure, and awaits both plain-file
and gzip stream completion. Object insertion order, JSON omission of
`undefined`/function/symbol properties, array `null` substitution, `toJSON`
keys, number handling, and the trailing newline are retained. A writer or
stream error rejects the writer and the driver run, so a failed capture cannot
be reported as successful.

Validation from the candidate worktree:

- `node --test scripts/parity-production/capture-writer.test.cjs scripts/parity-production/driver.test.cjs` — 8 passed, including bounded premature-close, already-destroyed-stream, listener-cleanup, and Unicode boundary checks.
- `python3 -m py_compile scripts/parity-production/run.py` and `git diff --check` passed.
- `node --check` passed for the driver, writer, and large-output harness under the pinned Node 8.9.4 image.
- Pinned image `node@sha256:8233daae003ba0ecba4e6d70cab8525c30a3f085935afc624a275892ebe23f7c` (`v8.9.4`) wrote and checked a 283,121,920-byte output, larger than 256 MiB; the temporary output was removed in-container.
- The same pinned image rejected a writable that destroyed itself during a backpressured write without hanging, and matched `JSON.stringify(report) + '\\n'` byte-for-byte for valid surrogate pairs, escaped characters, and unpaired surrogates at the 16 KiB boundary.
- Plain and gzip output round trips matched `JSON.stringify(report) + '\\n'`; delayed writable backpressure and an intentional sink failure were exercised.
- `scripts/parity-production/run.py` now hashes `capture-writer.cjs` with the other capture tools, so an original golden cannot be reused after a writer change.

Scope and limits: this is an isolated candidate based on `b654de598255ba023f33ff31656bfa5bc84057d4`. It has not recaptured the corpus or changed references, goldens, normalizers, the ledger, or robot files. Root must review the candidate and recapture affected controls because the driver hash changes. The serializer is intended for the report object produced by this driver; unsupported values such as `BigInt` still fail the capture and propagate that failure.
