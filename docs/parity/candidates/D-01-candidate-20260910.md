## 4. Cache semantics — what is actually demonstrated

The instruction was to be conservative here. Statements, split by strength:

**VERIFIED (observed in this worktree)**

* The cache stores `{relayData, lassoDataFromRedis:true, lassoInsertedIntoRedisAt}`
  and the hit response is that object re-serialised byte-for-byte; the hit
  content length is 107 B, matching the capture (`packages/data/test/relay-contract.test.js` D01/2).
* A miss writes the cache (after responding) for both GET and HEAD; a HEAD
  warms the cache and the following GET is a hit (D01/5, D01/9).
* Phoenix's `TTLCache` expiry is exact: with a mocked `Date`, an entry set at
  `t=0` with TTL 900 is a hit at `t=899999 ms` and a **miss with a live refetch
  at `t=900000 ms`**; the news entry is still a hit at that point and expires at
  `t=3900000 ms` (D01/16). This exercises the real code path — it is not a
  simulated result.
* A cache read that throws is non-fatal and the relay fetches live; a cache
  write that throws is non-fatal and the miss response still goes out (D01/14,
  D01/15).
* `?skipCache=false` (the string) skips the cache read and refetches;
  `?skipCache=` (empty) does **not** skip (D01/3, D01/4).

**INFERRED**

* The per-relay TTL *values* (900/3900/900) come from the subclass fields; the
  capture never let a TTL elapse, so 900/3900 are read from source, and the
  fact that the relay forwards `ttlSeconds` into `cache.set` is verified by
  D01/16's expiry behaviour.

**UNKNOWN — no claim**

* Whether the original Redis expired, evicted or re-set any key. The reference
  fixture used a fake Redis whose `set` never expires and whose `get` returns
  the raw map value (`capture.cjs:255-258`); Redis-side `EX` expiry, TTL
  refresh-on-read, `maxmemory` eviction and persistence across restart were
  **not** exercised and remain unverified.
* Whether a Redis GET/SET failure in the original produced the same observable
  result as Phoenix's in-process cache failure. The tolerance is read from
  source (lines 84-86, 124-131) and mirrored, but the original error paths were
  never executed.

## 5. Divergence candidates (not edited into DIVERGENCES.md)

1. **Cache substrate.** Reference: Redis (shared, persistent, server-side `EX`
   TTL). Phoenix: in-process `Map` (`packages/data/src/cache.js`). The
   single-process request/response contract matches; multi-instance sharing,
   persistence across restart and Redis eviction policy are unreproduced.
   Reasoning: the reference's Redis behaviour is UNKNOWN given the fake-Redis
   fixture, so this cannot be closed by inference.
2. **Calendar relay compatibility is still absent (D-04).** In the reference the
   calendar handlers *are* relay handlers: `cacheSecondsToLive = 60`, cache keys
   `google_calendar:<skillId>:<accountId>:<calendar>` /
   `outlook_calendar:...` (GoogleCalendarHandler.ts:16,60-62;
   OutlookCalendarHandler.ts:18,61-63), real HEAD routes via the base class, and
   credential-driven invalidation (`onNewCredentialArrived` →
   `redisClient.del(key)`, GoogleCalendarHandler.ts:26-35,
   OutlookCalendarHandler.ts:28-37). Phoenix's `packages/data/src/calendar.js:46-58`
   returns `{events}` with no envelope, no cache and no HEAD. The captured
   `relay-cache-miss` transaction (`{"relayData":{"events":[]},…}`) already
   proves the original wraps an empty calendar in `relayData`. Left to D-04.
3. **APNews poll/prefetch lifecycle absent (D-06).** `APNewsHandler.init()`
   polls every category and re-caches on an interval
   (`pollIntervalMS` default `hoursToMs(1)`), APNewsHandler.ts:36-63. No Phoenix
   equivalent.
4. **Upstream HTTP status is not surfaced on the real routes (D-05/06/07).** The
   relay now implements the reference `.response` contract (table row 4), but
   `openMeteoGet`/`defaultRssGet`/`defaultOrsGet` (`weather.js:35`,
   `news.js:43`, `maps.js:47`) still hardcode `e.status = 502` instead of
   attaching `{status, data}`. Today this is unobservable (both paths yield
   502), so I did not edit files owned by D-05/06/07. Reasoning recorded rather
   than guessed at a body shape.
5. **HEAD-with-provider-failure internals.** The reference double-sends on the
   already-ended HEAD response (line 107 after line 71), which Express turns
   into a thrown error handled by the outer `next(err)` (line 132-134). Phoenix
   returns. The client-visible result is identical (empty 200); the internal
   error path differs. INFERRED from source; not observed.
