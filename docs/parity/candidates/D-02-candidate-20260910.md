## What this candidate does

`packages/data/src/credentials.js` now reproduces the full lasso credential
contract and persists it durably:

1. **Required fields** (`Credentials.ts:35-47`, `:189-196`, `:242-248`):
   save requires `accountId skillId serviceName serviceAccountName scopes
   clientId` (+ `authCode` or token triple); find requires the five base
   fields; delete requires the four ids. Enforced in the same order as the
   reference (`requireProps` walks the array, `Missing <p> in request`, scope
   shape checks after presence).
2. **Scope handling**: `validateScopes` (array, non-empty, all strings);
   lookup uses `scopes: { $all: query.scopes }` semantics — fewer/extra
   stored scopes still match, a requested scope the stored credential lacks
   does not.
3. **Unique keys**: the store key reproduces the Mongo `credentials_index`
   compound index `(accountId, skillId, serviceName, serviceAccountName,
   scopes)` (`StoredCredential.ts:107-119`), scopes sorted for
   order-insensitivity. Two credentials for the same slot with different
   scopes coexist — the original "store google:personalCalendar credential
   with other scopes" fixture passes.
4. **Active/inactive lookup**: normal lookup hides `isActive: false`
   (`find(query)` uses the reference's `isActive: { $ne: false }`); save uses
   `allowInactive` and reactivates + clears error, exactly like
   `Credentials.find(data, true)` in `saveCredential`.
5. **Duplicate auth codes**: same authCode re-save throws
   DUPLICATE_KEY → HTTP 200 `{ credentialExists: true }`; a NEW authCode in
   the same slot replaces the oauth2 payload (`Credential.test.ts` "replace
   with new authCode" fixture).
6. **Wildcard deletion**: `skillId/serviceName/serviceAccountName` = `*`
   wildcards; scopes optional and skipped when `scopes[0] === '*'`.
7. **Cross-provider replacement** (`deleteOtherCredentials`): the six
   original deletion fixtures (deletion.test.ts) pass — google→outlook and
   outlook→google for personalCalendar and workCalendar; no deletion across
   different calendars or non-calendar serviceAccountNames.
8. **Durable state**: `new CredentialStore({ file })` (or a path string, or
   `ETCO_data_credentialsFile`) snapshots after every mutation with an atomic
   exclusive-tmp + rename write (0600 file, 0700 dir), following the
   account-service `Store` pattern. A store opened on the same file recovers
   all credentials ("survives restarts"); delete persists too. A corrupt
   snapshot fails loudly. With no file configured the store stays in-memory
   so existing tests remain hermetic; wiring a persisted store into the
   running service's default is a 1-line change in `packages/data/src/index.js`
   (root-owned per task file list).

## Verified / inferred / unknown

**Verified** (read source + executed tests):
- required-field sets/messages and ordering (`Credentials.ts` lines read
  above; HTTP 400 body asserted)
- scope validation and `$all` lookup semantics; scope sets coexist under the
  5-tuple key (original fixture)
- DUPLICATE_KEY duplicate-authCode handling and 200 `{credentialExists:true}`
- wildcard delete scoping (account2 fixture: account1 unaffected)
- cross-provider replacement, all four report-skill arms + two negative arms
- the assignment-bug regression fixture (Phoenix behavior) and the recorded
  divergence
- persistence across store/service restart (store-level and HTTP-level),
  atomic write, permissions, no tmp litter, corrupt-file failure, env-var
  path, delete-persists

**Inferred** (design choice, not directly pinned by reference):
- sorted-scopes keying makes scope-order rotations collapse to one record
  (the reference Mongo multikey unique index would treat
  `['a','b']`/`['b','a']` as distinct entries — latent dupe surface; Phoenix
  normalizes. No original fixture distinguishes).
- overlapping-scope saves (e.g. `['read']` then `['read','write']`) coexist
  in Phoenix, whereas Mongo's unique multikey index would reject the second;
  `find` multi-match falls through to `undefined` exactly like the
  reference's "critical bug" path (`Credentials.ts:221-226`).

**Unknown**:
- wire behavior of a real OOBE/settings client that sends `scopes` as a
  single comma-joined param (Phoenix parser keeps it as ONE literal scope;
  reference Express/qs would yield a string and `validateScopes` would 400
  — both are 400s but with different messages). Not exercised by any
  original fixture.
- Live Mongo enforcement of the unique index (code-level only; no Mongo in
  tests).
