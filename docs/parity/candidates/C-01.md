# C-01 candidate: shared HTTP response and error serialization

Status: working candidate; lead review and task verification remain pending.

This candidate is intentionally bounded to the source-confirmed common HTTP response/error boundary in `packages/common/src/service.js`. It does not claim C-01 parity or close the task.

## Source and differential basis

The frozen original source is the prepared reference tree at `.parity/reference/5c0a7390539663ba749d360de348a428c088505c`:

- `packages/utils/src/service/BaseService.ts` uses Express `res.status(...).json(...)` for handler results and errors, `res.status(...).send(...)` for `/healthcheck`, body-parser JSON plus `urlencoded({ extended: true })`, and `statusCode` from thrown errors.
- `packages/utils/src/service/handlers/BaseHttpHandler.ts` passes handler results directly to `res.status(200).json(result)`, so `null` remains `null` and `undefined` produces an empty response body.

The V-02 baseline (`docs/parity/evidence/2026-09-05/comparison/baseline`) records the public mismatches this candidate addresses: `null` and `undefined` became `{}`, empty JSON requests did not preserve the body-parser `{}` result, malformed JSON and form bodies were treated as internal errors, typed status `418` was lost, error envelopes carried Phoenix-only codes/messages, and responses lacked Express headers. The original HTTP fixture showed `application/json; charset=utf-8`, byte `content-length`, weak SHA-1 ETags for non-empty bodies, `x-powered-by: Express`, and `text/html; charset=utf-8` for health text.

## Candidate changes

- Preserve `null` and `undefined` handler results (`null` JSON and an empty JSON body respectively).
- Run the frozen `express@4.16.2` and `body-parser@1.18.2` middleware directly, including empty-body `{}`, repeated/extended urlencoded fields, strict JSON, content encoding/charset checks, default size and parameter limits, and safe `qs@6.5.1` prototype handling.
- Preserve the source's Node 8 JSON syntax-error text at the response boundary while retaining body-parser's actual parse/error classes and limits on the Node 22 candidate runtime.
- Translate the demonstrated Node 22 parser diagnostics for missing separators, invalid literals/numbers, invalid escapes, unterminated strings, and whitespace-sensitive token positions into the source's Node 8 wire messages without changing parser acceptance. A bounded syntax scanner supplies positions when modern V8 omits them; body-parser remains the validity authority.
- Preserve the restored Classic front door's `application/x-amz-json-1.1` JSON payloads, which are outside the frozen BaseService body-parser middleware but required by existing Phoenix consumers.
- Preserve a thrown numeric `statusCode` and serialize errors as `{ type, msgID, ts, final: true, data: { message } }`, including the original URL-not-found message.
- Centralize text/JSON response headers and body framing to match the observed Express contract: `x-powered-by`, content type, byte `content-length`, and weak SHA-1 ETag for non-empty bodies. ETag entity lengths use hexadecimal bytes, as Express's `etag` package does.
- Match the frozen Express boundary's trailing-slash routing, GET-to-HEAD fallback, automatic OPTIONS `Allow` response for registered fixture routes, and healthcheck method behavior.
- Match case-insensitive routes, body-parser-before-404 ordering, conditional 304 ETags, and the source healthcheck OPTIONS 404 boundary.
- Preserve the existing `rawBody` opt-out behavior from the worktree baseline.
