## Implemented behavior (`packages/classic/src/push.js`)

- `DeviceRegistry` — a durable, atomically persisted (JSON file, 0600,
  write-tmp + rename) per-account device store, the local counterpart of the
  source `AccountPush` Mongo collection.
  - `createDevice(accountId, {name, pushToken, type})` — upsert by name,
    revival; strips the pushToken from every other account ($pull semantics);
    implicit account creation; returns active devices. Type is *not* updated on
    re-register (source does not update it either).
  - `removeDevice(accountId, name)` — marks deleted; 404
    `ACCOUNT_NOT_FOUND` / `DEVICE_NOT_FOUND`; returns active devices.
  - `removeDeviceByToken(pushToken)` — token invalidation downstream effect.
  - `listDevices(accountIds)` — `{ accountId: [active devices] }` map.
  - `sendNotification(accountId, notification, provider)` — the
    MobileController-equivalent delivery path: one send per active device,
    provider failures contained (caught, never rethrown), and a provider that
    reports an invalid token triggers the downstream removal.
- Replaceable provider seam — `PushProvider` interface (`send({device,
  notification})` + optional invalid-token reporting) and a
  `FixturePushProvider` (records sends, can fail, can invalidate tokens).
- `makePushHandler` — `CreateDevice` / `RemoveDevice` over AWS-JSON-1.1:
  responses are the account's **active Devices list** (the pinned `Devices`
  output shape), validation errors are **422** `Boom.badData`-style, unknown
  operations are 400 `ValidationException`.

## Why the existing `keyPush.test.js` push slice changed

The previous stub returned `{}` and 400, which **contradicts** the pinned
source (list output, 422 badData, per-account ownership). The candidate changes
the protected surface, so the existing push test had to assert the correct
contract to stay green: list body, 422, and RemoveDevice with the owning
account's credential (an anonymous RemoveDevice of another account's device now
correctly 404s). The other three keyPush tests are untouched and pass.

## Tests added (`packages/classic/test/push.test.js`, 13 tests)

1. CreateDevice returns the active Devices list including the new device.
2. Re-register upserts pushToken and revives a removed device.
3. RemoveDevice returns the remaining active list.
4. CreateDevice validation is 422 for missing/invalid fields; unknown members allowed.
5. RemoveDevice missing name → 422; unknown device / unknown account → 404 with the right `x-amzn-errortype`.
6. Per-account ownership + single-owner pushToken (stale-token `$pull`).
7. Unknown operation → 400.
8. Registrations persist across registry instances (durable re-open).
9. A failed durability write rejects the mutation and rolls back.
10. Delivery reaches every active device through the fixture provider.
11. Provider failure is contained and does not stop other deliveries.
12. A provider-reported invalid token removes the device (downstream effect).
13. `removeDeviceByToken` pulls the token from every account.
