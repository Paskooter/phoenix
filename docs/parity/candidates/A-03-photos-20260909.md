Decorator trap was checked by reading `account.handler.ts` top to bottom:

- Mapping: `updatePhoto: { method: this.UpdatePhoto, options: { binary: true } }`.
- `UpdatePhoto`: the decorator immediately above the method is
  `@parseCredentials({})`. There is no `@validatePayload`. The handler passes
  `request.payload` itself as `dataStream`.
- `RemovePhoto`: the decorator immediately above the method is
  `@parseCredentials({})`. There is no `@validatePayload`. Payload is unused.

Both operations are credentialed at the source handler. The public Phoenix
face follows the accepted A-03/A-04 pattern: SigV4 on the Classic/Account
listener. `x-amz-credentials` is not a public caller switch.

## Candidate behavior

`packages/account/src/accountIdentity.js` adds `updatePhoto` / `removePhoto`
to `OPS` and `ACCOUNT_IDENTITY_METHODS`. They are **not** in
`ACCOUNT_ANONYMOUS_TARGETS`. `robotFace.js` still dispatches Account prefixes
through `handleAccountIdentity` and now threads the existing
`memberPhotoProvider`. Classic's raw-body proxy, already used for
`Loop.UpdateMemberPhoto`, also forwards `Account.UpdatePhoto` as a stream.

Controller order matches source:

1. `findById(ownerId)`
2. `createPublic({ dataStream, path: account._id.valueOf() + Date.now() })`
3. if `account.photoUrl`, `remove(photoUrl.split("/").pop())` — basename, not
   the full URL
4. `account.photoUrl = savedPhoto.url`; save

`removePhoto` deletes the basename when set, then persists `photoUrl = null`
even when no object existed. A failed remove/save does not roll back an
already completed binary write.

JSON projection uses the existing `accountToSourceJson`. `photoUrl: null` is
emitted; an unset field is omitted. `UpdatePhoto` / `RemovePhoto` return the
safe Account projection (no access keys), matching the handler which does not
call `toJSON({ unsafe: true })`.

Storage is the existing A-04 `MemberPhotoStorage` / `memberPhotoProvider`
seam. No second photo stack. Loop member photo tests remain green.

## Candidate divergences (for root to classify)

These are differences vs pinned source. They are **not** recorded in
`DIVERGENCES.md`. Root owns that file and the harmless/required decision.

1. **Local photo seam, not S3.** Source `BinaryController.createPublic`
   returns the S3 `Location`. Phoenix returns
   `${photoPublicBaseUrl}/${accountId}${Date.now()}` from the existing member
   photo adapter. Same replacement used by accepted A-04 member photos.
2. **Public identity is SigV4, not `x-amz-credentials`.** Source handler
   identity is `parseCredentials`. Phoenix Classic/Account identity is the
   signed access key, matching the other A-03 slices.
3. **Loop nested `account.photoUrl` after Account.RemovePhoto.** Source
   `LoopController.loadMembers` copies `photoUrl: account.photoUrl` onto the
   accepted member account, so a null would appear in ListLoops. Phoenix
   `copyAcceptedAccount` only copies when `photoUrl != null`, so ListLoops
   omits the field. Account.Get/RemovePhoto themselves emit `null`. This
   candidate does not change Loop populate.
4. **`AccountUpdated` postSave SNS** is not implemented. Photo mutations
   persist the document only. Same gap as the identity-core candidate.
5. **Shared `/member-photos` prefix.** Account and Loop member objects live
   in one directory/URL space. Source used one S3 controller with different
   path prefixes (`account._id + ts` vs `memberId + ts`). Collision is
   unlikely (different id namespaces) but the public path is Phoenix's.
